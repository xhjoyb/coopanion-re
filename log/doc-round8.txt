# 第八轮：「改包 → 重签」本机实证（MT MCP）+ 文档回改

日期基准：2026-10。样本：`apk/Coopanion-v12.71.apk`（137,205,527 B，md5 `ed319932e645eec9e080d86e409e00b1`）。

---

## 一、这轮解决了什么

`docs/00 §11` 优先级第 3 项原本是「做一次『改包 → 重签 → 冒烟』实证」。
上一轮结论是「本机缺 `java` / `apksigner` / `zipalign` / `keytool`，重打包实证做不了」，于是被挂起。

本轮换了路线：**不装 JDK，改用本机已运行的 MT MCP**。
`127.0.0.1:8786` 上跑着 **MT MCP v0.2.0**（JSON-RPC 2.0 over HTTP，57 个工具），
其中 `mt_apk_build(sign=true)` **自带签名器**。结果是「改包 + 重签」在本机 2.1 s 完成，
**不需要把 137 MB 上传到 GitHub / 任何云端**（原计划的 CI 路线因此降级为备选，未采用）。

结论先写：**`docs/04 §2` 那句「无自校验、重签即可」从推断变成了实证**；「冒烟」这一步仍未做。

## 三、三重独立校验（判断「改对了、没改坏」）

| # | 手段 | 结果 |
|---|---|---|
| 1 | 条目级对比（CRC32 + 压缩/原始大小 + 压缩方法，29 条） | **25 条完全一致**；变化仅 `AndroidManifest.xml` + `META-INF/MANIFEST.MF`；`assets/payload.asset` CRC 前后同为 `0x8eaf26c6` |
| 2 | `MANIFEST.MF` 摘要跨包比对（26 段） | **25 段 SHA-256 相同**，唯一不同是 `AndroidManifest.xml` 段 |
| 3 | 自研 `axml.py` v3 解码新旧 manifest 后 `diff` | 都是 63 行，**唯一差异就是 `versionName` 那一行** |

附：`zipfile.testzip()` → `None`（29/29 CRC 实测通过，0.9 s）；
v1 签名链纯标准库自校验 → `MANIFEST.MF` **26/26 摘要正确**、`.SF` 对 `MANIFEST.MF` 整包摘要 **MATCH**、`X-Android-APK-Signed: 2,3`；
两包 APK Signing Block 同为 **4,088 B**，id-value 对 v2 `0x7109871a` + v3 `0xf05368c0` + padding `0x42726577`。

> 第 3 项是关键：`AndroidManifest.xml` 从 **6,544 B 缩到 5,064 B**，单看体积像「丢了东西」。
> 自研解码器证明这是 MT 重编码 AXML 时字符串池排得更紧，**语义完全等价**。

## 四、三个必须记住的副作用

1. **签名密钥不是原厂的**。MT 配置的是 **AOSP 平台测试密钥**：
   `C=US, ST=California, L=Mountain View, O=Android, OU=Android, CN=Android, emailAddress=android@android.com`，
   有效期 `2008-02-29 → 2035-07-17`，证书 SHA-256 `a40da80a…f5dc`（原件 `2793fcff…0764`）。
   ⇒ **同包名不同签名，不能覆盖安装**，必须先卸载原应用（丢数据）。
2. **`META-INF` 文件名会变**：`COOPANIO.SF` / `COOPANIO.RSA` → `ANDROID.SF` / `ANDROID.RSA`（密钥别名 `ANDROID`）。
3. **体积 +53,246 B**，全部来自重签；业务负载零增长。

## 五、MT MCP 的四个坑（已写进 `docs/04 §2`）

1. `mt_apk_dex_read_class_outline` **必须传 `limit`**，否则 `INVALID_ARGUMENT: Missing limit`（`retrySameArguments=false`）。
2. `mt_apk_read_text` 正文在 **`data.textWindow.text`**，不在 `data.text`。
3. `mt_apk_build` 的 `outputName` **不接受子目录**（Home 文件名或绝对路径），`dir/x.apk` 报 `Invalid outputName`。
4. 文件策略默认 `{"/": deny}` + Home `/storage/emulated/0/MT2/mcp`；包被 `mv` 出 Home 后 `mt_apk_workspace_open` 查不到（返回 `data=`）。

## 九、真机冒烟（补做，通过）

环境：Android 16 / SDK 36，KernelSU（`ksu`），Android 侧 shell 走 `super_admin:shell`（proot 里看不到 `/system/bin`）。

### 9.1 安装过程与两个坑

| 步骤 | 命令 | 结果 |
|---|---|---|
| 落地 | `su -c cp` 到 `/data/local/tmp/coopanion.apk` + `chmod 644` | md5 `a2386187…2502` 与源文件一致 |
| 首次安装 | `pm install -r` | **失败** `INSTALL_FAILED_UPDATE_INCOMPATIBLE`（原版已装） |
| 卸载（保数据） | `pm uninstall -k` | `Success`，但包记录变 `installed=false` 且带旧签名 |
| 再装 | `pm install -r` | **仍失败**（`-k` 的残留记录照样挡） |
| 彻底卸载 | `pm uninstall`（不带 `-k`） | `Success`，`dumpsys` 已无该包 |
| 安装 | `pm install -r` | **Success** |

坑：**`pm uninstall -k` 不能用来绕签名冲突**。它保留的数据记录仍携带旧证书，安装器照样拒绝；必须先彻底卸载。
另：用 root 也无法备份应用数据——`/data/data/com.palai.prootsmoke` 与 `/data/user/0/…` 在 ReSukiSU
「应用数据隔离」下对本命名空间直接不存在（`ls` 报 No such file），`/data/misc/iopgp/<包名>` 里只有 perfetto trace（每个应用都约 5 MB，不是业务数据）。
