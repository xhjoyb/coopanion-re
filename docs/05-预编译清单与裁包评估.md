# 05 · payload 预编译清单与裁包评估（P3）

> 目标：把 `assets/payload.asset` 里的 `node_modules`、原生 `.node`/`.so`、以及运行库逐项列清，
> 标出**运行时必需**与**可裁**，为 P4 的确定性重打包（`build-payload.py`）定输入。
>
> 一句话结论：**整包重压没有收益（ratio 0.994），P4 的收益只能来自删条目**；
> 有把握的可裁体量约 **112 MB 原始 / 60~75 MB 压缩后**，主要来自三份重复的
> `libonnxruntime.so`（省 2 份）、嵌套重复的 sherpa native 包（省 1 份）、
> 构建期工具链 `esbuild`/`@esbuild`、以及 Android 上永不加载的 `koffi` 与从不被调用的 `npm`。
> **订正（cut-sym5）**：上面那句里的「构建期工具链 `esbuild`/`@esbuild`」是误判 —— `tsx` **运行期**
> 依赖 esbuild，删掉后 core 直接 `ERR_MODULE_NOT_FOUND` 起不来；详见 §4.B 与 `BASELINE.md`。

## §1 方法与可信度

四源交叉，全部一致，因此下列数字可直接当 P4 的输入：

| 来源 | 条目 | 文件字节和 | 说明 |
|---|---|---|---|
| 自写 `tarfile` 流式扫描（`tools/p3_manifest.py`） | 5,096 | 357,069,438 | 输出 `mcp_out/p3.tsv`（`kind/size/linkname/path`） |
| busybox `tar tvzf -`（管道直读 zip 内流） | 5,096 | — | `4053 -` / `957 d` / `86 l` 与 TSV 逐类一致 |
| `log/rootfs_list.txt` 历史快照解析 | 5,096 | 357,069,438 | 早期 `tar tvf` 存档 |
| 512 字节块级解析（`tools/p3_tarstruct.py`） | 5,096 + 22 长名头 | 357,069,438 | 定出 tar 真实总长 `360,825,344` |

**上一轮怀疑「文档的 `360,825,344` 有 22,528 B 差额」已被证伪——差额是我自己重算时漏了 22 个 GNU 长名头**：

```
条目累计   hdr 2,609,152 + pad 1,123,202 + files 357,069,438  = 360,802,816
GNU LongLink  22 个头 × (512 头 + 512 名)                      =      22,528
EOF 零块     2 × 512                                           =       1,024
                                                      合计 = 360,825,344  ✅
```

`docs/00`、`docs/04`、`README.md`、`BASELINE.md` 里的 `344.11 MiB` / `ISIZE = 360,825,344` **是对的，不需要订正**；
`38.00%` 也对，口径是 `137,118,068 / 360,825,344`（payload.asset 文件大小 ÷ tar 长度），不是「压缩后 ÷ 解压后」。

## §2 容器结构（P4 复刻的字节级事实）

### 2.1 gzip 层

| 项 | 值 |
|---|---|
| 头 10 字节 | `1f 8b 08 00 00000000 00 ff` → magic gzip、CM=8 deflate、**FLG=0（无 FNAME/FCOMMENT/FHCRC）**、**MTIME=0**、XFL=0、OS=255 |
| **gz 文件大小** | **137,118,068 B**（= APK 内 `assets/payload.asset` 的 `file_size`） |
| APK 内再 zip 一层 | 136,348,624 B（zip deflate 尺寸，与 gzip 无关，勿混用） |
| 解压后 | 360,825,344 B |
| CRC32 | `0xbb9152eb` |
| ISIZE | 360,825,344 |
| 尾部多余数据 | 0（`post_gzip_eof_bytes = 0`，单成员 gzip） |

⇒ **压缩级别已实测：`compresslevel = 6`**。用 Python `zlib`（与原厂同一个 zlib 实现）level 6 + 手写固定头，重压出 **137,118,068 B / `sha256 39899fa0…`，与 APK 内 `payload.asset` 逐字节相同**。

level 9 反而更小（136,591,114 B，差 526,954 B）—— 所以不能想当然用 9。另注意 Python `gzip.compress(level=9)` 会把 XFL 写成 2，必须自己写头（XFL=0）。

### 2.2 tar 层

| 项 | 值 |
|---|---|
| 格式 | **混合格式**：前 **5,107** 条 GNU（`magic = "ustar  \0"`），末尾 **11** 条 POSIX ustar（`"ustar\0" + "00"`）；均为 512 字节块 |
| 条目 | 5,096 = 4,053 普通文件 + 957 目录 + 86 软链 + 0 硬链 |
| 扩展头 | **只有 GNU `L`（LongLink）22 个**；无 `K`、无 pax `x`/`g` |
| 结尾 | 2 个零块（1,024 B），之后无任何非零垃圾 |
| 元数据 | `uid/gid` 全 `(0,0)`；`uname/gname` = `('root','root')` × 5,086、`('','')` × 10；`mode` 六种见下、`mtime` **89 种**（min 0 / max 1792164366）；`magic` **两种**（见上「格式」行） |

`mode` 分布：`0o600` × 2,247、`0o644` × 1,713、`0o700` × 529、`0o755` × 520、`0o777` × 86（软链）、`0o1777` × 1（`/tmp`）。

**末尾 11 条 POSIX 条目是什么（P4-A 新发现）**：它们全是 `app/coop-stage/vendor/pet/web/` 下的 web UI（`app/{bubble,care,main,net,skins,talk,ui}.js`、`figure-host.js`、`pet-desk.js`、`pet-multi.js`、`pet-new.html`），**`mtime` 全为 0**、magic 为 POSIX。说明主 rootfs tar 打完之后，又用**另一个写入器**追加了一层 web UI 覆盖（中间没有零块分隔，是流式拼接）。这不是损坏，但重建时**必须逐条照写 magic 与 mtime**，否则 checksum 差 32（0o40），整块头就变了。

**22 个长名条目**（P4 必须用 GNU 长名头，不能截断；括号内为当初的 name 字节长）：

- pnpm 内嵌依赖 9 个：`exponential-backoff/…/skip-first.delay.js`(103)、`node-gyp/gyp/pylib/gyp/…` 6 个 `__pycache__/*.pyc`(101~111)、`packaging/…`（同组）
- npm 内嵌依赖 6 个：`@sigstore/protobuf-specs/dist/__generated__/google/**`(101~109)
- sherpa native 3 个：嵌套副本的 `libonnxruntime.so`(101)、`libsherpa-onnx-c-api.so`(107)、`libsherpa-onnx-cxx-api.so`(109)
- **home 运行残留 3 个**：`home/companion/data/runs/r-2026*/incidents/2026-10-06T*-uncaught-exception.json`(122)

最后 3 个是**运行时事故记录**（各 3,909 B），不是代码 —— 属 P4 可裁。

## §5 可裁收益（P4-B 实测，原估算已作废）

**原估算有一处算法错误**：把「原始大小 − 该组独立压缩后大小」当成收益（如嵌套 sherpa `40,305,256 − 13,511,959 = 26,793,297`）。删一个文件省下的是它**压缩后**的体积，不是差额。原表因此把 D 组多算了一倍，`60~62 MB` 那个目标不成立。

## §6 P4 复刻清单（硬约束）

1. **软链必须原样重建**
   - `bin/` 下 53 条（51 applet → `busybox`、`pnpm`、`npm`）；
   - `app/coop-stage/node_modules/` 4 条接线：`cortico → ../build/cortico`、`cortico-world-cua → ../vendor/cua`、`cortico-provider-coo → ../vendor/coo`、`cortico-world-desktop-pet → ../vendor/pet`，另有 `app/node_modules → ../node_modules`、`.bin/mime → ../mime/cli.js`；
   - 4 个子工程的 `node_modules/*` 共 22 条（`build/cortico` 5、`vendor/cua` 4、`vendor/coo` 4、`vendor/pet` 9）；
   - `lib/node_modules/pnpm/pnpm → node_modules/@pnpm/exe.linux-arm64/pnpm`；
   - `usr/bin/{env,node}`。
2. **22 个 GNU LongLink 头**：`name` 字节长 > 100 时必须写 `L` 头，不能截断；P4 用 Python `tarfile` 的 `format=tarfile.GNU_FORMAT` 即可自动处理。
3. **结尾 2 个零块**（1,024 B），不要写 record 对齐（当前 tar 没有 10240 对齐）。
4. **mtime 必须逐条保留，不要统一**（本条已被 P4-A 实测修正）：原厂是 89 种值混杂，且末尾 11 条为 0。想要逐字节等价，就必须从原 tar 逐条读出并写回，任何「统一成 0 / 固定常量」都会破掉等价性。
5. **gzip 头 + 级别**：`FLG=0`（不写 FNAME）、`MTIME=0`、`XFL=0`、`OS=255`；**`compresslevel = 6`**（实测，用 9 会变小且不等价）。
6. **保留 `mode` 差异**：`0o600` 是可执行文件与部分 JSON 的默认，`0o755` 给 `bin/*`、`0o777` 给软链、`0o1777` 给 `/tmp`。P4 若统一成 644/755 需先验证 `node`、`busybox`、`corepack` 与 51 个 applet 的可执行位。
7. **`boot.sh` 的自愈逻辑不要丢**：`librt.so.1 → libc.so.6` 三处软链、四个 native 拷到 `/app/sherpa-native`（绕 `proot --link2symlink` 的 `.l2s.` 伪目录）、`LD_LIBRARY_PATH` 五条路径。
8. **改长度会触发 rootfs 重建**：`run-core.mjs:13-16` 注释说明 Android 壳层按「版本号 + payload 长度」算指纹，指纹变就解压到新的 `rootfs-v8-*` 目录；`carryOverHome()` 会把上一份 `home/` 搬过来（过滤 `instance.lock` 与 `data/runs`）。P4/P5 验收时要利用这点验证「升级不丢记忆」。
9. **magic 也必须逐条保留**（P4-A 新增）：混合格式（5,107 GNU + 11 POSIX），不能全一律写 GNU。写完头后还要**重算 checksum**（chksum 区当 8 个空格，输出 `%06o\0 `）。

## §10 P6 · F 组规则与实证（`--groups F`）

### 10.1 规则

`p4_cut.py` 的 `rules('F')` **只剩一条**规则（第二条 `esbuild-native` 已删，见 §10.5）：

| label | 判定 | 命中 |
|---|---|---:|
| `dead-dep-subtree` | `./app/coop-stage/node_modules/<pkg>/` 且 `<pkg>` ∈ 12 个包名 | 130 条 / 5,633,808 B |
| ~~`esbuild-native`~~ | ~~`./app/coop-stage/node_modules/@esbuild/linux-arm64/`~~ | ~~2 条 / 10,289,644 B~~ **P6 真机证伪，已撤回** |

12 个包名：`bare-path` `bare-events` `bare-stream` `bare-fs` `bare-url` `tar-stream` `streamx` `b4a` `events-universal` `teex` `fast-fifo` `text-decoder`。

### 10.2 为什么是「闭合子树」而不是「5 个包」

`du` 量的是目录占用，`manifest.json` 量的是权威条目（差几千字节，因为前者含目录项本身）。
更关键的是依赖关系**不是线性的**：

```
cortico  --package.json 声明 tar-stream: 3.2.1-->（但 cortico/{src,dist,bots} grep 零命中 ⇒ 死依赖）
tar-stream        -> b4a, bare-fs, fast-fifo, streamx
streamx           -> events-universal, teex, text-decoder
bare-fs           -> bare-events, bare-stream, bare-url
bare-url          -> bare-path
events-universal  -> bare-events（仅 exports."bare" 分支）
```

只删 `bare-*` 5 个包，等于把 `tar-stream` / `streamx` / `b4a` 留成半个残骸，而 `bare-events` 仍被 `events-universal` 的 `exports` 引用。所以按**闭包**取，12 个一起。

### 10.3 闭合性证据（三层）

1. `find . -name package.json | xargs grep -l '"tar-stream"\|"streamx"\|"events-universal"\|"teex"\|"fast-fifo"\|"text-decoder"\|"b4a"'` → 只命中这 8 个包自己的 `package.json`（外加两个当时已改名为 `.off` 的）。
2. 全树 `grep -rn "require('tar-stream"` → 唯一命中 `./tar-stream/README.md:30` 与 `:152` 的示例代码。
3. `events-universal@1.0.1` 的 `exports` 三支：`bare` / `react-native` / `default`；Node 走 `default → require('events')` ⇒ `bare-events` 在 Node 下不可达。

### 10.4 两轮独立 trace（都全绿）

方法：在树里把目标目录 `mv` 成 `.off`（**不用 `cp -al`** —— proot 的 link2symlink 会毁源树），跑 `tools/p5_run_trace.sh`，跑完 `mv` 回并确认 `ls -d *.off | wc -l = 0`。

| 轮次 | 移走 | trace 行数 | rc | shutdown 六步 | 关键日志 |
|---|---|---:|---:|---|---|
| traceG | 5 个 `bare-*` | 3,827 | 0 | 全 ok | `web面板已启动 http://127.0.0.1:17788/`、`core已启动`、`眼睛已开` |
| traceH | 追加 7 个（共 12） | 3,824 | 0 | 全 ok | `err:0 / js-errors:0 / web-panel:1 / core-started:1` |

对照项（防管道静默失效）：`grep -c 'esbuild' traceG.log = 36`、`grep -c 'bare-' traceG.log = 0`、模块错误 0。
**注意** `traceX.log` 是 strace 的 `openat/statx` 输出，中文只出现在 `runX.txt`；对 `traceX.log` grep 中文必然为 0。

### 10.5 esbuild native 为什么**不能**走（真机证伪，已撤回）

原判据（**错的**）：`esbuild@0.28.2` 的 `lib/main.js` 里 `build` / `transform` / `formatMessages` 等导出全是 `() => ensureServiceIsRunning().xxx()`，据此认为 `require` 时不 spawn、二进制只在真正调 API 时才拉起；`tsx@4.23.15` 只在 fallback 转译时需要它，包内 Node **v24.21.0** 原生剥类型 ⇒ 走不到。

真机结果（cut6，2026-10-26 06:24 全新首启）：

> `Error: The package "@esbuild/linux-arm64" could not be found, and is needed by esbuild.`
> `at generateBinPath (esbuild/lib/main.js:2044)` → `esbuildCommandAndArgs (2114)` → `ensureServiceIsRunning (2271)` → `startSyncServiceWorker (2478)` → `Object.<anonymous> (2519)`
> `[4] core 进程结束 rc=1` → `[WEB-ERR] -6 net::ERR_CONNECTION_REFUSED @ http://127.0.0.1:17788/`

关键点：**`main.js:2519` 是模块顶层语句**，不是导出函数。`require('esbuild')` 当场就走 `startSyncServiceWorker()` → `generateBinPath()`，压根不存在「惰性」。所谓「导出全是惰性包装」只对 `build` / `transform` 这些成员有效，管不到模块加载阶段。

对照：JS 包 `esbuild` 单独删掉（cut-BCDE-sym）同样 `rc=1`，报 `ERR_MODULE_NOT_FOUND: Cannot find package 'esbuild'`（§5.1）。两次崩的入口不同、结论一致：**esbuild 的 JS 包与其平台二进制必须整套保留**，B 组与 F 组是同一条红线的两端。

为何本地 trace 没拦到：真机入口是 `[RUN] root=/app/coop-stage/build/cortico` 跑的完整 core，本地 trace 的命令链与之不完全相同；且 `strace` 只记 `openat/statx`，`generateBinPath` 拼路径失败是纯 JS 层抛错，不一定留下 syscall 痕迹。**本地 trace 只证明启动链，不替代真机路径。**

撤回动作：cut7 起 `rules('F')` 删除 `esbuild-native`，`@esbuild/linux-arm64` 全量恢复（2 文件 / 10,289,644 B + 3 目录条目）。cut7 真机首启已过（§10.7）。

### 10.6 回归自证：重打 cut5 + 逐块 tardiff

在信任 cut6 之前，先证明工具链能复现历史产物：

| 项 | 字节 | sha256 |
|---|---:|---|
| `p4_repack.py build manifest.cut5.json treeC`（重打） | 267,912,192 | `06365710a21ee50470f8e454f8a0e2557817c04d3b71e79e23883299d08cafa0` |
| 原 `cut_sym5.tar` | 267,912,192 | `e3201b959849e3def714168ecc0e8084ee4e9848539eb140b15b89462382c4db` |

字节数相同、sha256 不同。`tardiff.py` 逐 512 字节块比对（mode / uid / gid / mtime / chksum / type / link / magic / uname / gname + data 段），得 **header diffs found: 1**，唯一差异：

```
blk 1945  ./app/coop-stage/home/companion/data/core-state.json
size 148 == 148；data sha 5315d1b5… vs 31041144…
```

⇒ 旧 `cut_sym5.tar` 里这份 `core-state.json` 是**某次运行后的状态**，`treeC` 解出来的是原厂字节 —— **新产物更忠实**。这也是 cut6 与 cut5 之间除 F 组外唯一的内容变动。

同一手法用于 gzip：`p4_gzip.py` 默认 level 9，但已装机 APK 里的 payload 是 **L6** 压的。用 L6 重压 `cut_sym5.tar` 得 **108,089,925 B / sha256 `f277c8f34f37676384ca0191fd8f636384150ab269b7f214f48826e480891034`**，与 APK 内 `payload.asset` **逐字符相同** ⇒ 裁包规则 / tar 重打 / gzip 头手写三段全部过；此后 cut6 的任何差异只能归因于 F 组。

（附带事实：三个 asset 的 gzip 头实测均为 `1f8b0800` / `XFL=0` / `OS=255`。）

### 10.8 风险与回退

- F 组裁的是「声明但零引用」的死依赖。一旦将来 `cortico` 真的 `require('tar-stream')`（启用扩展安装的 tar 解包路径），会 `MODULE_NOT_FOUND`。回退：`--groups B,C,D,E` 重出一版。
- ~~`@esbuild/linux-arm64` 缺失只会在「tsx fallback…」时暴露~~ —— **该判断已作废，真机首启即 `rc=1`**；cut7 已全量恢复该目录，`rules('F')` 不再含任何 esbuild 相关条目。
- 因此 §9 的真机路径里**扩展安装**这一项仍是硬要求 —— 它是唯一能正面证伪 `dead-dep-subtree` 的路径。cut7 只证明「启动链 + Web 面板」不再受 esbuild 阻断，扩展安装尚未实测。
- 更上层的教训：**「导出是惰性包装」不能推出「模块加载无副作用」**。判一个包能不能删，必须看模块顶层的执行语句（`main.js` 尾部），不能只看 `module.exports`。
