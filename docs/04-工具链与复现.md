# 04 · 工具链与复现

> 本文记录一条**可复现**的路径：从 `Coopanion-v12.71.apk`（137,205,527 B）走到 `docs/01`–`docs/03` 里的每一条结论。
>
> 需要先说明一个前提：目标环境里**没有 JDK、没有 apktool、没有 jadx、没有 baksmali、没有 pip、没有 7z**。
> 所以本工程出现的这套「自写反汇编器 + 自写 AXML 解析器」不是偏好，是被环境逼出来的唯一可行解。
> 反过来说，这套工具本身也是交付物的一部分：**纯 Python 标准库、零依赖、可离线重跑**。

## 0. 环境事实（实测，不是假设）

| 能力 | 状态 | 实测值 |
|---|---|---|
| `python3` | ✅ | **3.14.5**（proot Alpine / musl） |
| `unzip` | ✅ | `/usr/bin/unzip` |
| `tar` | ✅ | **busybox 1.37.0** —— 注意 `tar --version` 的输出就是 `tar (busybox) 1.37.0` |
| `gzip` | ✅ | `/bin/gzip` |
| `node` | ✅ | `/usr/bin/node`（宿主自带；包内另有一份 123 MB 的 aarch64 node） |
| `java` / `javac` | ❌ | 不存在 |
| 签名 / 重签名 | ✅（走本机 MT MCP） | **MT MCP v0.2.0 @ `127.0.0.1:8786`**，自带签名器（AOSP 测试密钥），见 §2「重签实证」 |
| `apktool` / `jadx` / `baksmali` / `smali` | ❌ | 不存在 |
| `pip3` | ❌ | 不存在（装不了 PyPI 依赖） |
| `zip` / `7z` | ❌ | 不存在（需要压缩就用 `python3 -m zipfile`） |

由此定下三条工程约束：

1. **不碰 JVM 工具链**。谁提 apktool/jadx 都别去找，找不到；也不要建议「先装个 JDK」——这套环境装不上。**但重签不需要 JDK**：本机 MT MCP 自带签名器，见 §2「重签实证」。
2. **解析器必须自己写**，且只能依赖 `struct` / `zlib` / `os` 这类标准库。
3. **大文件一律流式处理**。137 MB 的 APK 里 99.94% 是那一个 `payload.asset`，任何「先全读进内存再处理」的写法都会把设备拖死。

> busybox 的 `tar` **不支持 `--wildcards`**。这是本篇最容易踩的坑之一：从 tar 里只取一个子树，要用成员名前缀（`tar -xz -C dir ./app`），而不是 GNU tar 的通配符写法。这条已实测可用（见 §4）。

## 2. 阶段 0：先确界（zip 清单 + 签名）

任何逆向的第一步都不是「反编译」，而是**搞清楚代码到底在哪**。

```bash
cd Coopanion_v12.71
unzip -l apk/Coopanion-v12.71.apk > log/ziplist.txt
cat log/ziplist.txt
```

结果只有 **29 个条目**，且体积极端倾斜：

| 条目 | 大小 | 占比 |
|---|---|---|
| `assets/payload.asset` | **137,118,068 B** | 99.94% |
| `lib/arm64-v8a/libproot.so` | 264,105 B |   0.19% |
| `classes.dex` | 98,744 B | 0.07% |
| `lib/arm64-v8a/libandroid-shmem.so` | 66,681 B | 0.05% |
| `resources.arsc` | 2,440 B | 0.002% |
| 其余 24 个（res/ 图标、META-INF、probe js） | 合计 < 250 KB | — |

这个分布直接决定了后续路线：**业务逻辑不可能在 dex 里**（136 KB 的 dex 写不下一个 AI 桌宠），只能在 `payload.asset`。于是整个工程分成两条**互不干扰**的并行线：

- **线 A（dex）**：反汇编 → 还原 Android 壳层（Service / 悬浮窗 / 桥接）。
- **线 B（rootfs）**：解包 `payload.asset` → 拿 TypeScript 源码（业务本体）。

### 签名方案（影响后面能不能改包）

```bash
python3 - <<'PY'
import zipfile
z = zipfile.ZipFile('apk/Coopanion-v12.71.apk')
sf = z.read('META-INF/COOPANIO.SF').decode()
print('\n'.join(sf.splitlines()[:6]))
PY
```

输出里有一行很关键：

```text
Signature-Version: 1.0
Created-By: 1.0 (Android)
SHA-256-Digest-Manifest: 9vY83UFKsOAo5zAHDF01CC+D+9+TzZlZ/EwHyIrUytk=
X-Android-APK-Signed: 2, 3
```

- `X-Android-APK-Signed: 2, 3` ⇒ 这个包同时带 **v1（JAR 签名）+ v2 + v3**，不是「只有 v1」。
- 全文件搜 `APK Sig Block 42` 为真，EOCD 在偏移 `137,205,505`（= 文件尾 -22），符合 v2/v3 的「签名块紧贴中央目录之前」布局。

实践含义：**改动后必须重签**，三套方案会被签名工具一次性重算，不需要手工补 v2/v3；而本包没有自校验代码（见 `docs/01 §6`），重签不会额外触发检测。

### 重签实证（已落地，不再是推断）

环境里没有 `java` / `apksigner` / `zipalign` / `keytool`，但本机 `127.0.0.1:8786` 上跑着 **MT MCP v0.2.0**
（JSON-RPC over HTTP，57 个工具），**自带签名器**。于是「改包 → 重签 → 校验」可以在本机闭环，
不必把 137 MB 传到任何云端。客户端就是本工程的 `src/mt.py`（87 行，只用标准库）。

**① 先让 MT 独立复核原件**（顺带验证下面 §2 的结论不是自说自话）：

| 项 | MT MCP 返回 | 与自研工具 / 本节结论 |
|---|---|---|
| `counts` | `zipEntries 29 / dexEntries 2 / xmlEntries 2 / classes 124` | ✅ 完全一致 |
| `signature` | `schemes [V1,V2,V3]`、`hasDifferentCertificates=false`、证书 `sha256 2793fcff…0764` | ✅ 与「v1+v2+v3 共存、单证书」一致 |

**② 选一处可观测且零风险的改动**：

| 项 | 值 |
|---|---|
| 目标 | `AndroidManifest.xml` 的 `android:versionName` |
| 动作 | `12.71` → `12.71-mcp`（`mt_apk_edit_text` 的 `replace_match`，全文唯一匹配） |
| 版本戳 | `targetVersion` `33b9dda672474b5c` → `dc5f8afa22cf24fe` |
| 构建前检查 | `mt_apk_session_check(runBuildChecks=true)` → `buildCheckStatus=passed`、`changedZipEntries=["AndroidManifest.xml"]`、`changedClassCount=0` |
| 构建 | `mt_apk_build(sign=true)`，**2.1 s**，产物 **137,258,773 B**（+53,246 B） |
| 签名 | `signingPerformed=true`、`signSchemes=[V1,V2,V3]`、单证书 |

**③ 三重独立校验（均可复跑）**：

| # | 校验手段 | 结果 |
|---|---|---|
| 1 | 条目级对比（CRC32 + 压缩/原始大小 + 压缩方法） | 29 条全在；**25 条完全一致**；变化的只有 `AndroidManifest.xml` 与 `META-INF/MANIFEST.MF`；`assets/payload.asset` 的 CRC 前后同为 `0x8eaf26c6` |
| 2 | `MANIFEST.MF` 摘要跨包比对 | 两包都是 26 个条目段，**25 段 SHA-256 相同**，唯一不同的是 `AndroidManifest.xml` 段 |
| 3 | 自研 `axml.py` v3 解码两个 manifest 后 `diff` | 都是 63 行，**唯一差异就是 `versionName` 那一行** |

补充三条：

- `zipfile.testzip()` 返回 `None`（29/29 条目 CRC 实测通过，0.9 s）。
- v1 签名链自校验（纯标准库，不需要 RSA）：`MANIFEST.MF` 的 26 个条目摘要 **26/26 正确**；
  `.SF` 的 `SHA-256-Digest-Manifest` 与 `MANIFEST.MF` 实体 **MATCH**；`.SF` 内 `X-Android-APK-Signed: 2,3`。
- 两个包的 APK Signing Block 尺寸都是 **4,088 B**，id-value 对均为 v2 `0x7109871a` + v3 `0xf05368c0`
  + verity padding `0x42726577`。

**④ 三个必须记住的副作用**：

1. **签名密钥不是原厂的**。MT 用的是 **AOSP 平台测试密钥**：
   `C=US, ST=California, L=Mountain View, O=Android, OU=Android, CN=Android, emailAddress=android@android.com`，
   有效期 `2008-02-29 → 2035-07-17`，证书 SHA-256 `a40da80a…f5dc`；原件的证书是 `2793fcff…0764`。
   ⇒ **同包名、不同签名，不能覆盖安装**，必须先卸载原应用（并丢掉应用数据）。
2. **`META-INF` 里的文件名会变**：`COOPANIO.SF` / `COOPANIO.RSA` → `ANDROID.SF` / `ANDROID.RSA`
   （`ANDROID` 就是密钥别名）。
3. **`AndroidManifest.xml` 从 6,544 B 缩到 5,064 B**。这不是内容丢失（第 3 项校验已证明语义等价），
   是 MT 重编码 AXML 时把字符串池排得更紧。

**⑤ MT MCP 的四个坑（下次直接用，省半小时）**：

- `mt_apk_dex_read_class_outline` **必须传 `limit`**，否则 `INVALID_ARGUMENT: Missing limit`（且 `retrySameArguments=false`）。
- `mt_apk_read_text` 的正文在 **`data.textWindow.text`**，不在 `data.text`。
- `mt_apk_build` 的 `outputName` **不接受子目录**：只能是 Home 里的文件名或绝对路径。写 `dir/x.apk` 会报 `INVALID_ARGUMENT: Invalid outputName`。
- 文件策略默认 `{"/": deny}` + Home `/storage/emulated/0/MT2/mcp`。包一旦被 `mv` 出 Home，
  `mt_apk_workspace_open` 就找不到它（返回 `data=`）。所以「改完先留在 Home，校验完再移走」。

**⑥ 真机冒烟：已做，通过**（Android 16 / SDK 36）：

| 项 | 结果 |
|---|---|
| 安装 | 先 `pm uninstall` 原版 → `pm install` 重签包 → **Success**。注意「`pm uninstall -k` 保留数据」会让包记录带旧签名残留，依旧报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，**必须彻底卸载** |
| 版本校验 | `dumpsys package` → `versionName=12.71-mcp`、`versionCode=1271`、`primaryCpuAbi=arm64-v8a` |
| 启动 | `am start -n .MainActivity` → pid 存活、`topResumedActivity=com.palai.prootsmoke/.MainActivity` |
| 崩溃 | `logcat -d -b crash` **空**（无 FATAL、无 Native） |
| 业务链路 | 应用自身日志：`web面板 http://127.0.0.1:17788/` → `core已启动` → `World 已启动: terminal / desktop-pet` → `桌宠悬浮窗已启动 -> http://127.0.0.1:7797/pet` |

⇒ 重签包不只是能装，**还能跑**：`libproot.so` 拉起 node、原样 TS 跑起来、WebView 控制台与桌宠悬浮窗均正常。
`docs/00 §11` 的「改包 → 重签 → 冒烟」三项至此全部闭环。

## 3. 阶段 1：AXML 解码（`axml.py`，101 行）

`AndroidManifest.xml` 是二进制 AXML。结构是「一串 chunk」：

| chunk type | 含义 |
|---|---|
| `0x0003` | 文件头（同时是 `assert` 的判据：不是这个值就不是 AXML） |
| `0x0001` | string pool（字符串池） |
| `0x0180` | resource map（属性名 → 资源 id 的映射） |
| `0x0100` / `0x0101` | start / end namespace |
| `0x0102` / `0x0103` | start / end element |

脚本要点（都在 `src/axml.py` 里能对上）：

- **字符串池两种编码**：`flags & 0x100` 为真走 UTF-8（长度是两段 uleb：UTF-16 长度 + UTF-8 字节数），否则走 UTF-16LE（长度 u2，最高位 `0x8000` 表示需要拼第二段 u2 取高位）。
- **属性值必须按 `TypedValue.type` 分支**，不能把 raw data 当字符串：

| type | 含义 | 处理 |
|---|---|---|
| `0x03` | string | 去字符串池取值 |
| `0x12` | boolean | `data != 0` |
| `0x01` | reference | 打 `@0x%08x` |
| `0x10` | int dec | 十进制 |
| `0x11` | int hex | `0x%x` |
| `0x02` | attribute | 打 `?0x%08x` |

用法与输出：

```bash
python3 src/axml.py src/x/AndroidManifest.xml
```

```text
xmlns:android="http://schemas.android.com/apk/res/android"
<manifest versionCode="1271" versionName="12.71" compileSdkVersion="35" ... package="com.palai.prootsmoke" ...>
  <uses-sdk minSdkVersion="24" targetSdkVersion="35">
  <uses-permission name="android.permission.FOREGROUND_SERVICE_SPECIAL_USE">
  ...
```

**属性命名空间（v3 起自动还原）**：脚本解析 `0x0180` resource map，按每个 attr 资源 id 的高字节补前缀——
`0x01xxxxxx` 打 `android:`，其余非零 id（应用自身的 `0x7f……`）保留成 `0x7f010000:` 这类原值，
id 为 0 的（`package`、`platformBuildVersionCode`）保持裸名。因此现在直接输出
`android:versionCode="1271"`、`android:name="android.permission.INTERNET"`，`docs/01 §2` 不必再人工补。
（v2 及更早版本把 map 整个跳过，输出的是裸名 `versionCode`。）

## 4. 阶段 2：rootfs 抽取（`payload.asset`）

### 4.1 先判断「是什么格式」

```bash
python3 - <<'PY'
import zipfile
z = zipfile.ZipFile('apk/Coopanion-v12.71.apk')
i = z.getinfo('assets/payload.asset')
print('zip compress_type =', i.compress_type, 'stored_size =', i.compress_size)
with z.open(i) as f:
    print('magic =', f.read(8).hex())
    f.seek(-8, 2)
    import struct; crc, isize = struct.unpack('<II', f.read(8))
    print('gzip isize =', isize)
PY
```

实测：

- `compress_type = 8`（deflate）、`compress_size = 136,348,624`，而 `file_size = 137,118,068` ——**zip 这层几乎没压掉东西**（0.56%）。
- `magic = 1f8b0800` ⇒ 里面是 **gzip**。
- gzip 尾部的 `ISIZE = 360,825,344` ⇒ 解开后是 **344.11 MiB 的 tar**，压缩比 38.00%。

### 4.2 只列清单（不落盘，5096 条）

```bash
unzip -p apk/Coopanion-v12.71.apk assets/payload.asset \
  | tar -tzv > log/rootfs_list.txt
wc -l log/rootfs_list.txt     # 5096
```

清单里能一眼看到「运行时」的骨架：

```text

./bin/busybox                1,914,704 B
./lib/aarch64-linux-gnu/libc.so.6  1,722,920 B   ← glibc 2.39
./usr/bin/node -> /bin/node
```

### 4.3 只解业务子树（跳过 123 MB 的 node）

```bash
mkdir -p src/rootfs
unzip -p apk/Coopanion-v12.71.apk assets/payload.asset \
  | tar -xz -C src/rootfs ./app
```

- busybox tar 用**成员名前缀**过滤，`./app` 就只解这一棵子树；**不要**写 `--wildcards './app/*'`（busybox 不认）。
- 跳过 `./bin` 省下 123,024,744 B —— 二进制对本任务无价值，我们只要源码。
- 校验点：`ls src/rootfs/app/coop-stage/run-core.mjs`、`src/rootfs/app/boot.sh` 都在。

结果 `src/rootfs/app` 为 137.1 MB（`coop-stage/node_modules` 119.2M + `vendor` 14.1M + `build` 3.4M + 其余）。

## 5. 阶段 3：DEX 反汇编（核心，3 个脚本 + 3 次自举补丁）

### 5.1 为什么可以手写

| 指标 | 值 |
|---|---|
| `classes.dex` | 98,744 B |
| `classes2.dex` | 37,212 B |
| 类总数 | **124**（`classes.dex` 101 + `classes2.dex` 23） |
| 定义方法总数 | **544**（124 个类的 `.method` 合计；其中 `-$$Nest$` 桥接 **55**） |
| `PetWindowService` 方法数 | 45（含 **25** 个 `-$$Nest$` 桥接方法，占全工程 55 个的 45%） |

这个规模用「纯 Python 逐指令解码」完全可行，不需要工业级反编译器。

### 5.2 数据流

```text
classes*.dex
   │  dexdump.py（149 行）      结构层：strings / types / protos / fields / methods / class_data
   ├─→ log_strings*.txt         字符串表（找注入脚本、日志文案、密钥常量）
   ├─→ e_classes*.txt           类继承关系
   ▼
dex2smali.py（486 行）          指令层：code_item → 逐条指令文本
   │  ├─ patch_decode.py（101 行）  指令格式解码补丁
   │  ├─ patch_fields.py（138 行）  字段 + 访问修饰符补丁
   │  └─ fix_indent.py（21 行）     指令行缩进修正
   ▼
java2/classes.dex.smali（449,149 B） + classes2.dex.smali（163,100 B）
   │  split_smali.py（29 行）
   ▼
java2/classes/*.smali           124 个「一类一文件」
```

一条命令跑通（结构层）：

```bash
python3 src/dexdump.py src/x/classes.dex strings  > src/log_strings1.txt
python3 src/dexdump.py src/x/classes2.dex strings > src/log_strings2.txt
python3 src/dexdump.py src/x/classes.dex classes  > src/e_classes.txt
```

### 5.3 dex2smali 的「自举补丁」机制（重要，复现时别乱序）

`patch_decode.py` / `patch_fields.py` / `fix_indent.py` **不是运行时插件**，它们是「**修改 `dex2smali.py` 源码的脚本**」——读完目标文件、按片段替换、再写回。
所以：

1. 正确顺序是 **`dex2smali.py`（原始版）→ patch_decode → patch_fields → fix_indent → 开始反汇编**。
2. 这三个脚本**只对未打补丁的原始文件幂等**。在已打过补丁的文件上重跑，`old` 片段不再匹配，轻则 no-op，重则把文件改坏。
3. 复现时最稳的做法：**直接用仓库里现成的 `dex2smali.py`**（已经是打完补丁的状态），不要去重跑三个 patch。

三个补丁各自修了什么（可对照脚本里的注释）：

| 脚本 | 修的 bug | 症状 |
|---|---|---|
| `patch_decode.py` | `21c` 分支把 `const-class` / `check-cast` 也当字符串解；`21h` 未左移 16；`22t`/`22s` 的 4 位寄存器对；`35c`/`45cc` 的 G 寄存器位置；`3rc` 空列表；`31i` 未区分 int/long；`51l` 未跨 4 个 code unit | 出现 `const-string v0, "com.foo.Bar"` 这种张冠李戴，或字面量全成 0 |
| `patch_fields.py` | 原版完全不打 `.field`，也不打访问修饰符 | 字段表是空的，无法读 `static final` 声明 |
| `fix_indent.py` | 指令行被多缩进了 4 空格 | 输出看起来像嵌套块，没法直接比 smali 风格 |

### 5.4 支持的指令格式（实测清单）

`10x 12x 11n 11x 10t 20t 22x 21t 21s 21h 21c 23x 22b 22t 22s 22c 30t 31t 31i 31c 32x 35c 3rc 45cc 51l`

**未覆盖**：`22cs` / `35cs` / `3rms`（这三个只在优化过的 odex 里出现，普通 APK 不会有）、`4rcc`。
本包的 124 个类没有一条指令落在这四个格式里（否则反汇编会打出 `?fmt` 而不是指令名）。

**数据块（v3 起）**：`packed-switch` / `sparse-switch` / `fill-array-data` 引用的 payload 不再丢——
payload 位置输出 baksmali 风格的 `:pswitch_data_N` / `:sswitch_data_N` / `:array_N` 块
（`.packed-switch` / `.sparse-switch` / `.array-data` 到 `.end …`），case 目标同时打上 `:pswitch_N` 等标签，
**case 值 → 目标地址的映射在 smali 里直接可读**。target 偏移按 Dalvik 规范以「switch 指令地址」为基准。
本包命中 1 处：`VoiceBridge.errName(I)`（9 个 case，key 1..9）。

### 5.5 输出格式

```text
.class Lcom/palai/prootsmoke/PetWindowService;
.super Landroid/app/Service;

.field private static final TAG:Ljava/lang/String;

# direct access=0x2
.method private Lcom/palai/prootsmoke/PetWindowService;->focusImeAndShow()V
    # registers=5 ins=1 tries=1
    const-string v0, "[PET] 已请求 IME（hasFocus="
    iget-object v1, v4, Lcom/palai/prootsmoke/PetWindowService;->imeProxy:Landroid/widget/EditText;
    ...
.end method
```

- `# registers= / ins= / tries=` 是 `code_item` 的三个头字段，**`ins` 决定参数个数**（`ins=1` 表示无参实例方法，`ins=2` 表示 1 个参数）。
- `# direct access=0x…` 里 `0x2` = `private`、`0x1` = `public`、`0x10000` = 构造器（synthetic/direct）。
- `-$$Nest$m` / `-$$Nest$fget` / `-$$Nest$fput` / `-$$Nest$s` 是 **R8 为内部类访问外部私有成员生成的桥接方法**。这类方法一出现，就等于告诉你「这里有个匿名类/lambda」。

### 5.7 已知缺陷（v3 已修 2 条，其余如实登记）

1. ~~**`22s` 格式的寄存器高 8 位没右移**~~ **（v3 已修）**。`22s` 的布局是 `op | A(4bit) | B(4bit) | lit16`，
   正确取法 `A = (unit >> 8) & 0xf`、`B = (unit >> 12) & 0xf`（旧版把整个高位字节当寄存器号）。
   本包 5 处受影响指令全部还原成三操作数：`and-int/lit16 v3, v3, #255`（原 `v51`）、
   `rsub-int/lit16 v8, v8, #700`（原 `v136`）、`rsub-int/lit16 v8, v8, #500`（原 `v136`）、

   已用 `diag_units.py` 对原始 unit 复核（`EyesService.imeHeightOf` 的 `0x18d0` → A=8、B=1）。
2. **少数 `invoke` 的成员签名被拼错**，生出 `Landroid/widget/TextView;->setTextSize` 这类不存在的成员（真实是 `Landroid/widget/TextView;->setTextSize(F)V`）。判断时看「类名 + 方法名」就够，不要纠结参数列表。
3. **不解析 `debug_info` / `annotations`**，所以没有行号表、没有注解信息；`try/catch` 只打区间，不打异常类型。
4. ~~**不解析 `packed-switch` / `sparse-switch` 的 payload**~~ **（v3 已修）**。现在直接输出
   `:pswitch_data_0` + `.packed-switch 0x1` 的 9 行 target，并给每个目标打 `:pswitch_N` 标签。
   `VoiceBridge.errName(I)` 的映射可一步读出，且与 `SpeechRecognizer` 常量值完全自洽：
   `1 网络超时` / `2 网络错误` / `3 录音出错` / `4 识别服务出错` / `5 客户端错误` /

   与第二轮「手工解 payload」的结论一致（`key 9` 目标地址最小、`key 1` 最大），互为交叉验证。

## 6. 阶段 4：`static_values` 取证（`read_static.py`，140 行）

### 6.1 为什么必须单独写这个工具

`PetWindowService` 里有 8 个 `static final`，其中 `PET_HOST_SHIM` 是 1,062 B 的 JS 脚本。
正常思路是去 `<clinit>` 里读赋值——但：

```bash
grep -n clinit src/java2/classes/com.palai.prootsmoke.PetWindowService.smali
# 无输出
grep -c '^\.method' src/java2/classes/com.palai.prootsmoke.PetWindowService.smali
# 45
```

**本类没有 `<clinit>`**。原因：javac 把 `static final String/int` 常量做了**编译期折叠**，所有使用点都被替换成字面量，字段本身变成死字段，初始化代码根本没生成。
于是这些值只剩一个地方：`class_def_item` 里的 `static_values_off` 指向的 `encoded_array`。

### 6.2 DEX 结构坐标（写解析器用）

`class_def_item` 固定 32 字节：

| 偏移 | 字段 |
|---|---|
| +0 | `class_idx` |
| +4 | `access_flags` |
| +8 | `superclass_idx` |
| +12 | `interfaces_off` |
| +16 | `source_file_idx` |
| +20 | `annotations_off` |
| +24 | `class_data_off` |
| **+28** | **`static_values_off`** |

`encoded_array` = `uleb(size)` + 连续 `encoded_value`。
每个 `encoded_value` = `uleb(header)` + 载荷，其中：

```text
vtype = header & 0x1f
varg  = (header >> 5) & 0x07
payload 长度 = varg + 1 字节（数值类型）
```

`vtype` 支持：`0x00 BYTE / 0x02 SHORT / 0x03 CHAR / 0x04 INT / 0x06 LONG / 0x10 FLOAT / 0x11 DOUBLE /
0x17 STRING / 0x18 TYPE / 0x19 FIELD / 0x1a METHOD / 0x1b ENUM / 0x1c ARRAY / 0x1d ANNOTATION /
0x1e NULL / 0x1f BOOLEAN`。

### 6.3 用法与实测输出

```bash
cd src
python3 read_static.py x/classes.dex 'Lcom/palai/prootsmoke/PetWindowService;'
```

```text
class_data_off=0x17dcf static_values_off=0xde6a
count=8
[0] CHANNEL      = 'coopanion_pet'
[1] packageName  = 'pet_alpha'
[2] packageName  = 8801
[3] PET_HOST_SHIM= '(function(){ ... })(...)'     ← 1062 B，与 src/js/inj_01.js 逐字一致
[4] packageName  = 'http://127.0.0.1:7797/pet'
[5] packageName  = 'coopanion'

```

**这个输出直接改写了两个结论**：

- `TOUCH_SIZE` 真值是 **700**，不是早期文档写的 520；而 `grep TOUCH_SIZE` 只有字段声明一行 ⇒ **它是死常量**。

`field_ids` 取 `name_idx` 用 `+4`、`static_fields` 的 `field_idx` 按 diff 累加，两处对齐后三个类的字段名全部正确：

## 9. 阶段 7：走读纪律（怎么保证「不是猜的」）

这套流程能出 `docs/01`–`03` 那种密度，靠的是三条固定动作：

### 9.1 先建方法索引，再读方法

```bash
grep -n '^\.method' src/java2/classes/com.palai.prootsmoke.PetWindowService.smali
```

一行一个方法 + 行号，等于免费拿到「类的方法表 + 物理布局」。后续所有 `sed -n 'A,Bp'` 都基于它。

### 9.2 认 `-$$Nest$` 桥接方法 = 找到匿名类

```bash
grep -c '\-\$\$Nest\$' src/java2/classes/com.palai.prootsmoke.PetWindowService.smali
# 25
```

25 个桥接方法（全工程 55 个，这个类占近一半），对应 `$1 … $17` 那批匿名类。**桥接方法名本身还告诉你它访问了什么**：
`fgetimeProxy`（读字段）、`fputlastProbeLog`（写字段）、`mpushTextToPage`（调方法）、`sm_isComposing`（静态方法）。
按这个规律，不需要读匿名类内容就能先画出「谁碰了谁」。

### 9.3 日志文案是最高价值的锚点

国产 App 的 `Log.i(TAG, "[PET] ...")` 往往比代码本身更能说明意图。本工程的很多结论是从日志串反推的：

| 日志 | 推出的结论 |
|---|---|
| `[PET] 触摸层已挂载 520x520` | 触摸层初值 520×520（不是 `TOUCH_SIZE=700`） |
| `[PET] 已请求 IME（hasFocus=…）` | `focusImeAndShow` 的唯一排障入口 |
| `inputFocus=… -> NOT_FOCUSABLE ON/OFF` | 极易读反：ON/OFF 指 `inputFocus`，不是 flag |
| `[DIAG] probe box=[…] focused=…` | 矩形链路的采样点（1 s 限流） |

### 9.4 冲突处理规则

**文档与字节码不一致时，一律以字节码为准**，并在文档头部写「修订记录」。
`docs/02` 的 v2 修订（16 处）就是这个规则的产物：`TOUCH_SIZE` 700、`CHANNEL`、两层 flags 6/4 个、`sizeTouchTo(x,y,w,h)`、`applyInputFocus` 的真实作用、`ImeCommitConnection` 是内嵌类。

## 11. 环境层踩坑清单（12 条，全是真踩过的）

1. **别找 JVM 工具**。没有 java/javac，apktool/jadx/baksmali 一律跑不起来，也不要想 `pip install`。
2. **busybox tar 不认 `--wildcards`**。取子树用成员名前缀 `./app`（已实测）。
3. **`sed -n '/<clinit>/,/^.end method/p'` 在双引号里会被 shell 展开 `$`**，导致「范围永远不匹配、只打印自身」甚至 `sed: write error`。用单引号，或直接 `grep -n`。
4. **`edit_file` 必须同时给 `old`**。只给 `new` 会报 `Invalid tool invocation: old parameter is required`（本工程踩过一次）。
5. **heredoc 用 `<<'PY'`**。里面出现 `$15`、`$16$1` 这类名字时，绝不能落在双引号或 f-string 里。
6. **大文件不要 `cat`**。449 KB 的 smali 刷屏会截断工具结果，用 `sed -n 'A,Bp'` 取区间。
7. **`grep -c '^\.method'` 是确认「方法不存在」的最快手段**。`<clinit>` 就是这么排除的（45 个方法里没有它）。
8. **zip 时间戳越界**（`1983-15-10 00:00`）不能当构建时间证据。
9. **`du` ≠ 字节数**。报体积用 `os.path.getsize` 求和（863 文件 = 16,350,953 B，`du` 却是 17.8M）。
10. **`unzip -p | tar -xz -C dir`** 是标准写法，不需要 `-f -`；busybox 会自己从 stdin 读。
11. **137 MB 场景优先 `struct.unpack_from`**，不要先切片复制，否则内存翻倍。
12. **`.field` 后面的 `access=0x…` 是数字标志**，不是注解，读的时候要自己翻译（`0x2` = private）。
